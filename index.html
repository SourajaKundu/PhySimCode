Can a multimodal LLM watch a 2D or 3D physics video, work out its laws and parameter values, and write code from scratch that regenerates it?

PhySimCode is a benchmark of 160.6K procedurally generated physics videos covering 162 phenomena, rendered by two different engines (SciPy in 2D, PyBullet in 3D). Every video comes with the code that made it, its true parameter values and a step-by-step physics explanation, so a model's answer can be checked at every level.

The taskFrom pixels to physics to programs

    
A model watches a physics video and must emit (i) a structured chain-of-thought JSON (simulation, observation, physical law, parameters) and (ii) a self-contained Python script. We execute the script and compare the regenerated video against the input.

👁
(i) Video understanding
Extract visual features and track objects across frames.
Measured by human appearance equivalence and DINOv2 / VideoCLIP similarity.

      
∑
(ii) Physics understanding
Bind what it sees to what it knows: identify the governing law and estimate parameters.
Measured by law correctness vs. equivalence and parameter recovery (±20%).

      
</>
(iii) Programming
Write stable simulation code that handles boundary conditions and renders a video.
Measured by compile / run / video-save rates and CodeBLEU.

      
⟳
End-to-end
Does the regenerated video show the same physics as the input?
Measured by human ratings of physical plausibility and physics equivalence.

    

    
This is not retrieval or memorization: every sample uses randomly sampled parameters drawn from physically plausible ranges, so values must be inferred from visual dynamics. Models get the engine name and an experiment-agnostic code template, so the test measures physics understanding rather than familiarity with an engine.

  






  

    
Key findingsFour consistent gaps

    

      

        
4.5/5 vs 2.47/5

        
Knowing ≠ inferring

        
Nearly every model states physical laws correctly (>4.5/5), but the best (GPT-5 Mini) scores only 2.47/5 at recognizing the law demonstrated in the video.

      

      

        
7.7%

        
Parameters are rarely recovered

        
The best model (Claude Sonnet 4.6) names and estimates within ±20% only 7.7% of all ground-truth parameters.

      

      

        
κ 0.72 vs 0.20

        
Pixels ≠ dynamics

        
DINOv2 and VideoCLIP agree with each other (κ = 0.717) but barely with human judgments of physics equivalence (κ ≤ 0.205). Models match appearance and miss dynamics.

      

      

        
50.1% vs 83.1%

        
Open vs. closed code

        
Open-source code runs without error 50.1% of the time on average, versus 83.1% for closed models. Claude Sonnet 4.6 is the most reliable at 98.8%.

Dataset constructionExpert-curated, procedurally scaled, debiased

    

      

        
1
Ideation

        
4 human experts curate 69 simulation ideas. Claude Opus 4.7 and GPT-5.5 propose 300 more, and the experts keep 93 for implementability and clarity of the intended physics. That gives 162 experiments, each with a 3–4 line expert-written event description.

      

      

        
2
Coding & CoT

        
From the expert descriptions, Claude Opus 4.7 writes the simulation code and extracts the governing laws, equations and physical parameters into a 13-key chain-of-thought schema.

      

      

        
3
Rendering

        
Pipeline A (87 exps): SciPy RK45 ODE solving (rtol 1e-9) with Matplotlib, 30 fps, 12 s. Pipeline B (75 exps, “Kubric”): PyBullet at 240 Hz, pyrender + trimesh PBR, 480×480. Each experiment gets ≈ 100 × nrand samples.

      

      

        
4
Multi-round review

        
2–10 rounds of human-in-the-loop correction until each simulation is physically plausible, followed by cross-review for factual mistakes.

      

      

        
5
Debiasing

        
Three LLM rounds (Unicode → LaTeX/Python, physics fixes by GPT-5.5, comment stripping) make 14,700 substitutions with a total Levenshtein distance of 693.6K characters. Four experts then verify the result.

PositioningHow PhySimCode differs

    
Prior work splits into two lines that have not met. Property estimation from video recovers a handful of latent values but never a program. Physics code generation produces executable simulations but is text-conditioned and single-engine. PhySimCode closes the loop: video → laws + parameters + runnable code → regenerated video, scored against the input.

    

  






  

    
Further analysisIs the benchmark fair and robust?

    

      

        
No authorship bias toward Claude

        
The ground truth was first written by Claude. We rebuilt a matched 75-sample subset entirely with GPT-5.5 and computed difference-in-differences bias scores against six neutral models. If the benchmark favored Claude, Claude's scores would be strongly negative and GPT's strongly positive. Neither happens.

        

      

      

        
Rankings agree across ground-truth authors

        
Spearman ρ between model rankings on the Claude-authored and GPT-authored arms is positive on all 13 metrics (mean +0.775).

        

      

      

        
More frames ≠ better physics

        
With more frames, models name more of the right parameters but do not estimate them better. Rankings hold at every frame budget. The bottleneck is quantitative physical inference, not perception bandwidth.

        

        

      

      

        
A single ±20% tolerance is justified

        
We perturbed 108 parameters across 15 experiments by ±10% (1,080 re-renders). Normalized visual sensitivity is remarkably uniform: median 0.98, IQR [0.93, 1.05], and only 7 of 108 fall outside [0.6, 1.5]. No parameter is unobservable (min 0.48).

        

          

          
0.480.930.981.052.12

        

        
Statistically supported rankings

        
With 15 i.i.d. samples per experiment across 162 experiments, the per-model aggregate standard error is ≤ 0.010, i.e. a 95% CI of ±2% on every reported metric. The 2,430-sample subset supports the rankings at roughly 66× lower cost than the full corpus.

      

    


    

      
Limitations & real-world transfer

      
Rigid-body dynamics dominate the benchmark, and the videos are simulator-generated. These are the easy case, with no sensor noise, occlusion or lighting changes, and models still fail. Reporting failure without nuisance factors isolates the cause to MLLM capability. It is also the only setting where ground-truth mass, stiffness or restitution is known, so the ±20% parameter-recovery metric can be defined. MPM-based engines such as Genesis would naturally extend the benchmark to fluids and deformables.
